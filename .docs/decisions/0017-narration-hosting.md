# 0017 朗读在哪里生成

## 背景

- 一篇 5 分钟的文章约要 680 秒 CPU；单词和例句的读音要在用户查词时当场生成，用户点了播放就在等。
- Vercel Hobby 的函数最多运行 300 秒、1 个 vCPU、每月 4 小时 CPU，大约只够 20 篇文章；onnxruntime-node 能不能在 Vercel 上运行没有官方说法，模型加运行库也超过 250 MB 的函数包上限。
- 项目所有者要求正常使用时不花钱。

## 比较过的方案

- 文章：GitHub Actions（免费，但定时任务会延迟，仓库 60 天没有活动会被停用，日志公开）；Google Cloud Run（免费额度够用，要绑卡）；Railway 或 Fly.io（每月约 1 美元，要绑卡）。
- 单词和例句：GitHub Actions 按需触发（要等半分钟到两分钟）；Cloud Run 按需服务（几秒，冷启动十几秒）；Vercel 函数（没有验证过）。
- 合成程序的语言：TypeScript / Node.js；Python。
- 按需服务做到哪一步：只合成，把 MP3 返回给 Web 应用；合成后自己写进 Neon 存储桶。
- Cloud Run 的代码：同一个仓库同一个镜像；同一个仓库两个镜像。

## 决定

- 文章和单词、例句的读音都在 Google Cloud Run 上生成，用 TypeScript / Node.js。
- 收集任务是一个 Cloud Run 任务（Job），朗读服务是一个 Cloud Run 服务，两者各自运行在不同的实例上。
- 朗读服务收到文字，合成后自己写进 Neon 存储桶，返回对象键、大小、时长和用量；是否需要合成、记录音频和用量由 Web 应用负责。
- 代码在同一个仓库，入口在 `src/worker/`；一个镜像，不同的启动命令；Web 应用和 Cloud Run 用同一个提交部署。
- 限量：朗读服务最多 1 个实例、没人用时缩到 0；收集任务一次只运行 1 个；订阅源配置合计每天不超过约 10 篇文章。

## 理由

- Cloud Run 任务每月免费 24 万 vCPU 秒，服务免费 18 万 vCPU 秒，这个规模用不完。
- 按需服务几秒就能合成，不会排在文章合成后面。
- 收集任务本来就要有存储桶的凭据，朗读服务用同一个镜像和同一套凭据写桶，Web 应用不用再传一次音频。
- 一种语言、一个镜像、一次部署，维护最少。

## 代价

- 要维护 Google Cloud 项目，并绑定结算账户（保护见 0019）。
- 朗读服务冷启动要读 400 MB 的模型，大约十几秒。
- 朗读服务也持有存储桶的凭据。

## 何时重新考虑

文章数要超出免费额度时；冷启动影响查词体验时；Vercel 能直接运行朗读模型时。
