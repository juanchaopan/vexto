# 0009 数据迁移

## 背景

PostgreSQL 里有用户数据，表结构要随代码的版本一起变。Neon 存储桶里的音频完全是程序生成的，但重新生成要花 CPU，而 Google Cloud 的免费额度有限。朗读模型是固定版本的文件。

## 比较过的方案

- PostgreSQL：drizzle-kit 生成的 SQL 脚本；或者独立的迁移工具（如 Atlas、dbmate）。
- 音频：格式或声音变了以后，用重建命令重新生成；或者保留旧音频，只有新生成的用新版本。

## 决定

- PostgreSQL 用增量迁移：drizzle-kit 从表定义生成带编号的 SQL 脚本，从当前版本按顺序执行；合并后的脚本不再修改。staging 在 CD 部署时执行，生产在手动部署任务里执行，开发机和测试库在建库时执行。
- 音频不迁移，也不重建：每个音频记录生成时的声音和编码版本，换了声音或音质以后，只有新生成的音频用新版本，旧音频按存储规则慢慢淘汰。
- 朗读模型每个版本放在以版本命名的目录里，换版本就上传新目录并改配置。
- 没有重建命令。

## 理由

- 迁移脚本和 ORM 的表定义一致，不用多学一个工具。
- 不重建就不会一下子用掉大量 CPU 和免费额度。

## 代价

- 写错的脚本只能用新脚本来纠正。
- 换声音以后，新旧音频的声音会混在一起一段时间。

## 何时重新考虑

出现 drizzle-kit 表达不了的变更时；或者需要所有音频立刻换成新声音时。
